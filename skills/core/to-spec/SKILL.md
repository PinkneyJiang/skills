# 需求规范生成技能 (to-spec)

本技能提取当前对话上下文以及对代码库架构的理解，生成标准化的技术规格说明书（Spec）。
**无需对用户进行重新面试**；直接综合已知的所有事实、决策与讨论共识。

项目的问题追踪系统与分诊标签规范应已在工程中就绪。如未提供，请提示用户先完成基础配置。

## 执行流程

### 1. 探索与上下文对齐
如果尚未完成，先探索代码库以了解当前代码状态。在整个 Spec 中统一使用项目领域词汇表（`CONTEXT.md`），并严格遵循相关区域内已有的架构决策记录（ADR）。

### 2. 勾勒测试接缝 (Seams)
草拟用于测试该特性的接缝。
- **优先使用已有接缝**，避免引入不必要的新接缝。
- 尽可能使用最高维度的接缝。
- 若必须引入新接缝，请在最高可用层级提出。
- 代码库中的接缝数量越少越好——理想数量是**单一接缝**。
- 与用户确认这些接缝是否符合预期。

### 3. 基于模板编写 Spec
使用下方的标准规范模板编写完整的 Spec，发布至项目问题跟踪系统，并打上 `ready-for-agent` 标签（无需额外的人工分诊）。

# [特性名称] 技术规格说明书

## 问题陈述 (Problem Statement)
站在**最终用户**的视角，清晰阐述用户当前面临的痛点、阻碍或未被满足的需求。

## 解决方案 (Solution)
站在**最终用户**的视角，描述本特性提供的完整解决方案及给用户带来的直观改变。

## 用户故事 (User Stories)
详尽、按序号排列的用户故事清单。每个用户故事必须严格符合标准格式：

1. 作为一个 <角色/Actor>，我希望 <实现某功能/Feature>，以便于 <获得某业务价值/Benefit>。

<user-story-example>
1. 作为一个手机银行客户，我希望能够在首页直观查看所有账户的实时可用余额，以便于我能基于财务状况更明智地规划当期消费。
</user-story-example>

用户故事清单必须极其详尽，无遗漏地覆盖该特性的所有核心场景、边界条件与异常分支。

## 实现决策 (Implementation Decisions)
明确记录在方案讨论中已经敲定的技术实现决策：
- 待新建或修改的核心模块；
- 待调整的模块公共接口签名与契约；
- 来自开发团队的技术澄清与共识；
- 架构分层与依赖流转决策；
- 数据库表结构与 Schema 变更；
- API 协议契约（HTTP 路径、入参 DTO、出参 VO、状态码）；
- 关键用户交互与状态机流转。

> ⚠️ **重要铁律**：严禁在 Spec 中固化具体的局部文件路径或临时代码片段，因为它们极易随时间推移而迅速过时失效。
> 
> *唯一例外*：如果早期原型产出了一段比自然语言能更精确表达决策的代码片段（例如有限状态机转换表、Reducer 函数、核心类型定义），可将其直接内嵌于对应的决策项中，并简要注明来源于原型。仅保留富含决策价值的核心骨架，绝不要贴出完整的演示 Demo。

## 测试决策 (Testing Decisions)
明确记录测试策略与决策：
- **良好测试的标准**：仅验证对外的公开行为，绝不绑定内部私有实现细节；
- 待覆盖的核心模块与接缝定义；
- 参考范例（代码库中现有的同类优质测试用例）。

## 不在范围内 (Out of Scope)
明确列出本阶段**明确不做**、留待后续迭代或故意排除的功能范围，防止范围蔓延（Scope Creep）。

## 补充说明 (Further Notes)
关于该特性的任何额外技术背景、性能考量、安全边界或第三方依赖说明。

# 疑难缺陷深度诊断技能 (diagnosing-bugs)

本技能专为处理疑难杂症与复杂性能退化而设计。必须严格执行各阶段纪律，**除非有明确且经过充分论证的正当理由，否则严禁跳过任何阶段**。

在探索代码库时，请先阅读 `CONTEXT.md`（若存在）以建立清晰的模块心理模型，并检查涉及区域的 ADR 决策记录。

---

## 敏感信息脱敏纪律 (Redact)

在排查过程中展示的命令、输出与捕获的排查产物，**必须预先完成敏感数据脱敏**：
- 将所有 Secret、Token、密码、敏感密钥替换为 `<REDACTED>`；
- 将测试回路构建在环境变量之上，确保凭证安全驻留在本地环境中，而非明文出现在日志或终端口令中；
- 抓取的网络请求与认证头：仅引用携带信号的关键行。
- 若脱敏后的日志不足以定位问题，应明确向用户说明并征求进一步支持。

## 阶段 1：构建紧致的反馈回路 (Build a Feedback Loop)

**这是本技能最核心的灵魂，其余一切不过是机械操作。**
如果你拥有一个**紧致且可靠**的成功/失败测试信号（即在该 bug 出现时能够稳定亮红），你就必然能定位根因；二分法查找、假设检验与插桩观测都只是在消费这个信号。反之，如果没有这个信号，对着代码盯得再久也无济于事。

在此阶段投入超常规的精力：**保持进取、发挥创意、永不轻言放弃。**

### 构建反馈回路的 10 大途径（按优先级排序）
1. **失败的自动化测试**：在能触及该 bug 的最高接缝处编写测试（单元测试、集成测试、E2E 测试）。
2. **Curl / HTTP 脚本**：针对正在运行的本地开发服务器发起精准请求。
3. **CLI 命令行调用**：提供固定测试输入，并将标准输出与预期正确快照做 Diff 对比。
4. **无头浏览器脚本 (Playwright / Puppeteer)**：驱动 UI 并在 DOM、控制台日志、网络请求上做断言。
5. **重放捕获的网络轨迹**：将真实生产发生的网络请求负载、事件日志落盘，在隔离环境中单独重放进目标代码路径。
6. **抛弃式微测试脚手架 (Throwaway Harness)**：启动系统的极小化子集（单个服务 + Mock 外部依赖），单次函数调用直击故障代码。
7. **属性/模糊测试回路 (Property / Fuzz Loop)**：若问题是"偶发计算错误"，用 1000 组随机入参批量压测，捕获异常模式。
8. **Git 二分定位脚手架 (Bisection Harness)**：若 bug 发生于两个已知状态之间（提交、数据版本），将"在状态 X 启动、验证、退出"流程自动化，接入 `git bisect run`。
9. **差分测试回路 (Differential Loop)**：将相同输入同时灌入新老版本（或两种配置），自动比对输出差异。
10. **人机协作交互脚本 (HITL Script)**：终极兜底方案。若必须人工点击，使用自动化脚本引导人工交互，并将捕获的现场信息结构化回传。

> 💡 **构建出正确闭环的反馈回路，Bug 就已经解决了 90%。**

### 持续收紧反馈回路 (Tighten the Loop)
- **速度**：能否更快？（缓存前置、跳过无关初始化、缩小测试范围）
- **信噪比**：信号能否更锋利？（精确断言该特定故障症状，而非单纯的"没有崩溃"）
- **确定性**：能否更可复现？（固定系统时间、锁定随机数种子、隔离文件系统、Mock 不稳定网络）

### 处理非确定性/偶发 Bug
目标不是追求一次性干净复现，而是**大幅提高复现概率**：将触发回路连续执行 100 次、并发压测、收紧时间窗口、注入微小 Sleep。50% 概率复现的 bug 完全可解，1% 概率则极难调试——持续强化压力直至其具有高复现率。

### 阶段 1 完成门禁：一个能够稳定亮红的紧致回路
必须能够指明**一条确切命令**（测试命令、脚本路径、curl 语句），且已在本地实际执行并展示脱敏输出，满足：
- [ ] **具备亮红能力 (Red-capable)**：真正走通故障路径并精确断言用户描述的具体症状；
- [ ] **确定性 (Deterministic)**：多次运行给出一致裁决；
- [ ] **极速 (Fast)**：耗时以秒计算，绝非数分钟；
- [ ] **Agent 可自动运行 (Agent-runnable)**：无需人工干预即可自主触发。

> 🛑 **红线警告**：若发现自己在尚未拿到该亮红命令前就去通读代码臆测原因，**立即停下**！未经实测验证的猜测是导致误诊的首要根源。

## 阶段 2：复现并最小化 (Reproduce + Minimise)

运行回路，目睹测试变红。
确认三要素：
- [ ] 确实精确复现了**用户所描述的症状**，而非旁边无关的报错；
- [ ] 多次运行稳定复现；
- [ ] 完整捕获异常现场（错误堆栈、脏数据快照、时延耗时）。

### 最小化缩减 (Minimise)
一旦稳定复现，立即将其精简为**依然能触发亮红的最小测试用例**：
- 逐一剔除无关输入、调用方、中间件、配置项与繁琐步骤；
- 每剔除一项就重新跑一次回路；
- 持续缩减，直到**所有剩下的元素都是不可或缺的承重点**（只要移除其中任何一项，测试就会变绿）。

---

## 阶段 3：建立多重假设 (Hypothesise)

在开始动手验证前，必须**同时提出 3–5 个具备竞争关系的假设并排序**。
严禁只建立单一假设——人脑倾向于锚定在第一个闪现的念头并产生证实偏差。

每个假设必须**具备可证伪性 (Falsifiable)**：
> 格式规范："如果是 <原因 X> 导致了该故障，那么 <改动 Y> 将会使 bug 彻底消失，或者 <改动 Z> 将会导致故障成倍恶化。"

**在动手验证前，优先将排好优先级的假设列表向用户展示**。用户往往拥有独特的领域认知，能瞬间帮你重新校准优先级或排除已知盲区。

---

## 阶段 4：针对性插桩探测 (Instrument)

每次只针对阶段 3 中的某一个具体假设进行验证，**严格遵循单变量原则**：
1. **优先使用调试器/断点 (Debugger/REPL)**：一个精准的断点胜过十行日志输出；
2. **在关键边界打印结构化日志**；
3. **严禁无脑全局乱打日志**。

**关键规约**：所有调试日志必须携带唯一可检索前缀，例如 `[DEBUG-a4f2]`。排查完毕后，通过全局单一 Grep 即可 100% 彻底清除，绝无生产泄漏隐患。

---

## 阶段 5：修复并固化防退化测试 (Fix + Regression Test)

在实施修复**之前**，先写出防退化回归测试（Regression Test）。
- 将阶段 2 提炼出的最小复现用例转化为工程接缝处的正式测试用例；
- 亲眼见证测试在未修复代码上亮红；
- 实施最精炼的代码修复；
- 亲眼见证测试变绿；
- 重新运行阶段 1 构建的全量反馈回路，确保原始完整场景彻底通过。

---

## 阶段 6：现场清理与闭环验收 (Cleanup)

在宣布排查结束前，执行强制清单检查：
- [ ] 原始故障场景彻底不再复现；
- [ ] 新增的防退化测试顺利通过并纳入测试套件；
- [ ] 彻底清除所有带 `[DEBUG-...]` 前缀的临时插桩代码；
- [ ] 删除所有临时生成的测试脚手架；
- [ ] 在 Commit 消息中清晰写明经过验证的根本原因与修复机制，为后人留下宝贵资产。

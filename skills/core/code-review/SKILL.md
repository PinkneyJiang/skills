# 工业级双轴代码审查技能 (code-review)

本技能对当前分支（`HEAD`）与用户指定的基线（Commit、分支、Tag 或 Merge-Base）之间的差异进行**严谨的双轴解耦审查**：
- **规范轴 (Standards)**：代码是否完全契合当前仓库既定的代码规范与工程设计准则？
- **契约轴 (Spec)**：代码是否 100% 忠实实现了需求规格说明书或关联任务工单的要求？

> 💡 **为什么要坚持双轴解耦？**
> 一次代码提交可能在一个轴完美通过，而在另一个轴彻底失败：
> - 遵循了所有代码规范，但做出了错误甚至多余的业务逻辑 → **规范通过，契约失败**；
> - 完美达成了所有业务需求，但违背了仓库分层架构并引入了严重的代码异味 → **契约通过，规范失败**。
> 双轴独立汇报可确保任何一个维度的问题都不会被另一个维度的光环所掩盖。

## 审查执行五步法

### 1. 锁定审查基线 (Pin the Fixed Point)
明确用户指定的基线参考点（Commit SHA、分支名如 `main`、`HEAD~3` 等）。
- 确认基线有效：`git rev-parse <fixed-point>`；
- 生成差异比较命令：`git diff <fixed-point>...HEAD`（三点式，对齐共同祖先）；
- 查看变更日志：`git log <fixed-point>..HEAD --oneline`。

### 2. 溯源需求契约 (Identify the Spec Source)
按以下优先级获取需求依据：
1. Commit 消息中关联的 Issue / 需求编号（如 `#123`, `Closes #45`）；
2. 用户作为参数传入的具体文档路径；
3. 仓库内 `docs/`, `specs/` 下与分支名对应的设计文档；
4. 若均不存在，明确向用户确认；若用户声明"无需求文档"，契约轴将标记为"无可用契约"并跳过该子项。

### 3. 确立规范依据与 12 大坏味道基线 (Standards Sources & Smells)
除仓库内现存的 `CONTRIBUTING.md`、`CODING_STANDARDS.md` 之外，规范轴始终强制挂载 **Martin Fowler 12 大经典代码坏味道基线**：
1. **神秘命名 (Mysterious Name)**：函数、变量或类型名称无法清晰传达其意图；
2. **重复代码 (Duplicated Code)**：相同或高度近似的逻辑在多处硬编码复制；
3. **依恋情结 (Feature Envy)**：一个方法过度访问另一个对象的数据，而非聚焦自身实体；
4. **数据泥团 (Data Clumps)**：一组字段或参数总是一起出现，暗示其应当被抽象为独立类型；
5. **基本类型偏执 (Primitive Obsession)**：用原始基本类型替代本该拥有自身约束的领域值对象；
6. **重复的 Switch/If 级联 (Repeated Switches)**：在多个地方反复出现对同一种枚举状态的判断分支；
7. **散弹式修改 (Shotgun Surgery)**：单一业务变动被迫分散修改很多不同文件；
8. **发散式变化 (Divergent Change)**：一个模块因为多种截然不同的业务原因被频繁修改；
9. **夸夸其谈未来性 (Speculative Generality)**：引入了当前需求根本用不上的抽象过度设计；
10. **过长的消息链 (Message Chains)**：类似于 `a.b().c().d()` 的穿透式级联调用；
11. **中间人 (Middle Man)**：一个类或函数几乎不做任何事，只是一味地向下层透传调用；
12. **被拒绝的遗赠 (Refused Bequest)**：子类继承了父类却重写或故意忽略了绝大多数行为。

### 4. 启动双子代理并行深度审查
- **规范子代理**：聚焦代码坏味道、架构违例、命名清晰度、未处理的边界异常与坏味道；
- **契约子代理**：逐行比对 Spec 中的验收准则，查验遗漏要求、范围蔓延（未要求的多余功能）与逻辑理解偏差。

### 5. 聚合呈现审查报告
按 `## 规范轴审查 (Standards)` 与 `## 契约轴审查 (Spec)` 两个章节分别客观输出问题清单，并在最后给出单行总结（各轴发现的严重缺陷数与最值得关注的核心问题）。

# 代码库架构治理与深模块演化技能 (improve-architecture)

本技能用于全面探测代码库内部的架构摩擦，识别将"浅模块 (Shallow Module)"重构为"深模块 (Deep Module)"的高价值演进机会。核心宗旨是提升系统的**可测试性 (Testability)**与 **AI 可导航性 (AI-Navigability)**。

本技能强依赖 `codebase-design` 所建立的架构词汇体系（模块、接口、深度、接缝、适配器、杠杆率、局部性）。在分析和沟通中必须严格统一术语，禁止混用 component、service、API 等泛化模糊词汇。

---

## 执行全流程

### 阶段 1：定向探索 (Explore)

**核心原则：以演进价值为导向，切勿过度设计 (YAGNI)。**
深模块带来的收益，主要体现在让未来的变更和维护更轻盈。因此，应将最大的审查权重放在近期频繁变动的核心代码路径上：
1. **排查热点**：通过 `git log --oneline` 回溯近期提交历史，找出修改最频繁、缺陷最集中的文件聚集区；
2. **结合领域模型**：阅读 `CONTEXT.md` 与现有架构决策记录（`docs/adr/`），明确系统的核心概念与历史权衡；
3. **识别典型架构摩擦点**：
   - 理解一个业务概念是否需要在大量零散琐碎的微小模块间反复跳跃？
   - 是否存在大量**浅模块 (Shallow Modules)**——公开接口的理解成本几乎与内部实现复杂度相当？
   - 是否存在仅仅为了写单测而强行抽离的纯函数，但真实业务 Bug 却隐藏在调用方复杂的编排与组装中（丧失了**局部性 Locality**）？
   - 紧密耦合的逻辑是否跨越了不该存在的接缝四处渗透？
   - 哪些核心业务流程因接口设计过浅而极难通过公开接口进行黑盒测试？

> 💡 **删除测试法则 (The Deletion Test)**：面对一个疑似浅模块，想象将其直接删除。如果系统复杂度凭空消失了，说明它只是个无意义的传递层；如果复杂度重新散落蔓延到了 N 个调用方，说明它确实承担了关键杠杆职责。

---

### 阶段 2：生成交互式可视化 HTML 报告 (HTML Report)

为了让架构问题与演进方向一目了然，将诊断结果生成为**独立的纯静态 HTML 报告**，存放在操作系统临时目录（避免污染业务仓库）：
- 路径遵循 `<tempdir>/architecture-review-<timestamp>.html`；
- 使用操作系统原生命令自动为用户打开展示；
- 采用 **Tailwind CSS (CDN)** 进行现代化响应式排版，采用 **Mermaid.js (CDN)** 渲染清晰的关系与时序图表。

#### 候选重构卡片核心字段规范：
每个架构重构建议卡片必须清晰呈现：
1. **涉及文件 (Files)**：关联的核心模块与路径列表；
2. **痛点摩擦 (Problem)**：阐明当前架构在理解、测试或维护层面造成的摩擦与阻碍；
3. **解决方案 (Solution)**：用精炼清晰的技术语言描述如何折叠浅模块、加深公开接口并沉淀内部复杂度；
4. **收益分析 (Benefits)**：从**局部性 (Locality)**、**杠杆率 (Leverage)** 与**可测试性 (Testability)** 三维度定量阐述；
5. **架构演进对照图 (Before / After Diagram)**：左右并排直观呈现重构前后的接缝位置、接口表面积与复杂度流动；
6. **推荐等级 (Strength Badge)**：明确标注 `强力推荐 (Strong)`、`值得探索 (Worth Exploring)` 或 `投机探索 (Speculative)`。

报告结尾附带 **最优突破口推荐 (Top Recommendation)**，给出明确的优先级实施建议。

---

### 阶段 3：深度追问与闭环实施 (Grilling Loop)

当用户从报告中选定一个突破口后，启动深度方案追问：
- 逐一推演约束条件、依赖关系、新深模块的输入输出契约、接缝后方的私有逻辑以及现存测试的去留；
- **同步更新领域模型**：若重构过程澄清了概念定义或产生了新核心术语，立即同步刷新 `CONTEXT.md`；
- **记录架构决策 (ADR)**：若用户基于重大的非显而易见权衡拒绝了某项建议，主动将其记录为 ADR，防止未来团队反复踏入同一讨论陷阱；
- **双重设计比选 (Design-It-Twice)**：针对关键深模块接口，并行设计两套截然不同的接口方案，从深度、杠杆率和接缝合理性上优中选优。

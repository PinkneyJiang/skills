# 现代代码库设计与深模块准则 (codebase-design)

本技能旨在为设计**深模块 (Deep Modules)** 提供统一的语言体系与架构原则：
**小接口背后蕴含大实现，置于干净清晰的接缝之上，并通过该公开接口实现完备的高效测试**。

统一的术语体系是高效架构协作的基础。在交流与设计时，必须严格使用以下标准词汇，禁止用模糊的 "component"、"service"、"API" 或 "boundary" 代替。

---

## 核心词汇表 (Glossary)

### 1. 模块 (Module)
任何具备**一个接口**和**一个内部实现**的软件单元。刻意与物理规模解耦：可以是一个纯函数、一个领域类、一个独立包、或是跨层切片。
*(杜绝使用模糊词汇：unit, component, service)*

### 2. 接口 (Interface)
调用方要正确使用该模块所**必须了解的全部知识总和**：不仅包括类型签名，还包括业务不变量、执行顺序约束、错误模式、必要配置以及性能特征。
*(杜绝将接口狭隘地理解为 TypeScript 的 interface 关键字或仅仅指 HTTP API)*

### 3. 实现 (Implementation)
模块内部的代码实体与私有逻辑。与**适配器 (Adapter)** 有着明确界限：一个组件可以是一个拥有庞大实现的微小适配器（如 Postgres 仓储），也可以是一个几乎无实现的庞大适配器（如内存 Fake）。

### 4. 深度 (Depth)
接口上的**杠杆率**。即调用方（或测试用例）每理解单位接口复杂度所能撬动的业务行为体量。
- **深模块 (Deep)**：小接口，大实现；
- **浅模块 (Shallow)**：接口复杂度几乎与内部实现相当（应当全力杜绝）。

### 5. 接缝 (Seam) *(Michael Feathers 定义)*
能够在不修改原处代码的前提下改变系统行为的位置；即模块接口所栖息的物理与逻辑位置。接缝设在何处是一个独立的架构决策，与接缝后方放置什么实现完全解耦。
*(杜绝使用 boundary，避免与 DDD 的界限上下文混淆)*

### 6. 适配器 (Adapter)
在接缝处满足并兑现接口契约的具象实现。描述的是**角色职责**（填补了哪个槽位），而非内部实质。

### 7. 杠杆率 (Leverage)
调用方从深模块中获得的巨大收益：学习极简的接口，却能驾驭极强的业务能力。一次接口定义，在 N 个调用方和 M 个测试用例中持续获得红利。

### 8. 局部性 (Locality)
维护者从深模块中获得的收益：变更、排错、知识与校验高度内聚于单一模块内部，绝不外溢到调用方。一次修复，处处生效。

## 深模块 vs 浅模块架构对比

```text
┌──────────────────────────────────────┐
│        深模块 (Deep Module)          │
│  ┌────────────────────────────────┐  │
│  │   精简接口 (Small Interface)   │  │  ← 极少方法、简单清晰的入参
│  ├────────────────────────────────┤  │
│  │                                │  │
│  │    深邃实现 (Deep Logic)       │  │  ← 封装复杂状态流转与业务规则
│  │                                │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
  VS
┌──────────────────────────────────────┐
│        浅模块 (Shallow Module)        │
│  ┌────────────────────────────────┐  │
│  │   庞大接口 (Large Interface)   │  │  ← 繁琐参数、暴露过多内部细节
│  ├────────────────────────────────┤  │
│  │    单薄实现 (Thin Logic)       │  │  ← 仅仅做了一层浅薄透传 (应当消灭)
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

## 核心架构原则

1. **深度是接口的属性，而非实现的规模**：一个深模块内部可以由许多精巧解耦的子函数组成，但这些子逻辑并不对外部公开。
2. **删除测试法则 (The Deletion Test)**：想象删掉该模块。如果复杂度凭空蒸发了，说明它只是个无意义的浅传递；如果复杂度重新散落到调用方各处，说明它具备不可替代的承重价值。
3. **接口即测试表面 (Interface is Test Surface)**：外部调用方与自动化测试跨越的是同一道公开接缝。如果你发现测试不得不穿透接口去嗅探内部状态，说明模块形状设计错误。
4. **单个适配器是假想接缝，两个适配器才是真实接缝**：不要过早为了"未来可能变动"而设计复杂的抽象接口，直到系统中确实存在两套不同的具象实现。
5. **双重设计法则 (Design It Twice)**：面对核心深模块，至少并行勾勒出两种截然不同的接口范式，在杠杆率与局部性上对比定夺。

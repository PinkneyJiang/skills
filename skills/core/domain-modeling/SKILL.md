# 领域建模与统一语言技能 (domain-modeling)

在软件系统设计与重构的全周期中，主动建立并持续锐化项目的领域模型。
**这是一门主动性极强的核心工程纪律**：主动挑战模糊术语、构建极端边界场景、并在共识达成的瞬间立即固化词汇表与架构决策。

> ⚠️ **技能定位**：仅仅在日常编码中*阅读* `CONTEXT.md` 只是常规习惯；本技能专门用于**定义、演化、审查与重塑**领域模型本身。

## 仓库结构标准

### 单一上下文工程（绝大多数中小型仓库）
```text
/
├── CONTEXT.md                     ← 全局领域统一语言词汇表 (Glossary)
├── docs/
│   └── adr/                       ← 架构决策记录集
│       ├── 0001-event-driven.md
│       └── 0002-postgres-storage.md
└── src/
```

### 多上下文工程（微服务 / Monorepo 复杂系统）
```text
/
├── CONTEXT-MAP.md                 ← 领域上下文映射图谱
├── docs/adr/                      ← 全局通用架构决策
└── src/
    ├── ordering/
    │   ├── CONTEXT.md             ← 订单子域统一语言
    │   └── docs/adr/              ← 订单特定决策
    └── billing/
        ├── CONTEXT.md             ← 计费子域统一语言
        └── docs/adr/
```

> 💡 **按需延迟创建原则**：仅在有真实内容需要沉淀时才创建对应文件。首个术语确立时创建 `CONTEXT.md`，首个重大权衡达成时创建 `docs/adr/`。

## 研讨期间的核心动作规范

### 1. 主动对齐并维护统一语言 (Challenge Against Glossary)
当团队成员或代码实现中出现了与 `CONTEXT.md` 现有定义冲突的词汇时，立即提出并修正：
> *"词汇表中明确将 '退单 (Cancellation)' 定义为整单终止，但当前讨论中你似乎是指部分商品退货。我们应该使用哪个标准术语？"*

### 2. 锐化模糊与多义语言 (Sharpen Fuzzy Language)
遇到含义过载或模糊的术语时，主动推导并提议规范的标准名词：
> *"此处提到的 '账号 (Account)' 究竟是指商户主体 (Tenant/Merchant)，还是指具体的登录凭证用户 (User)？这是两个具有完全不同生命周期和权限边界的核心概念。"*

### 3. 用具象极限场景压测概念边界 (Discuss Concrete Scenarios)
在梳理实体与状态关系时，通过极端的具象业务场景进行压力测试：
- *"如果同一用户在支付完成前的毫秒内取消了订单，状态机如何跃迁？"*
- *"如果租户欠费但存在正在进行的直播推流，资源所有权归属于谁？"*

### 4. 业务表述与底层代码交叉审计 (Cross-Reference with Code)
当发现业务规则的口头表述与底层代码实现存在偏差时，必须第一时间暴露冲突并消除隐患：
> *"口头说明支持按百分比部分退款，但数据库 Schema 的退款记录字段仅关联了整笔订单 ID 且缺少明细行绑定。代码与业务规范脱节，以何者为准？"*

### 5. 零延迟内联维护 CONTEXT.md
术语一旦澄清，立即就地同步更新 `CONTEXT.md`，严禁堆积滞后。
- **纯粹性原则**：`CONTEXT.md` 必须是**纯粹的业务领域词汇表**，坚决剔除任何框架、代码实现、数据库字段等技术细节，保持其作为业务共识基石的超然地位。

### 6. 严守 ADR 沉淀门禁（克制记录）
仅当同时满足以下三项条件时，才应当沉淀为 ADR：
1. **高逆转成本 (Hard to Reverse)**：未来推翻该决定的代价极其高昂；
2. **缺乏上下文时反直觉 (Surprising without Context)**：未来的开发者阅读代码时会困惑"为什么当初不采用更常见的做法？"；
3. **真实权衡的产物 (Real Trade-off)**：存在多个切实可行的候选方案，团队基于明确理由进行了取舍。

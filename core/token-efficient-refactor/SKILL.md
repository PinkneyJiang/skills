# Token-Efficient Refactor Skill（大工程 AI 重构省 Token SOP）

本技能沉淀自 .NET→NestJS 全工程自动重构实战（389 接口规模），解决 Agent 重构"Token 如流水"的核心问题。原则：**凡是能用脚本确定的，绝不消耗 Token；凡是模型要做的，只喂它必需的最小上下文。**

---

## 1. 契约先行：用脚本把「真值」从代码里抽出来（AST 预处理）

在让模型动手前，先用解析脚本把机器可读的真值提取成 JSON（而非让模型通读源码）：

- **提取什么**：路由/接口清单、DTO 字段与注释、鉴权标记、枚举值、配置键——即"范围边界 + 行为契约"。
- **怎么用**：真值 JSON 驱动后续三件事——①生成（模型只读契约+单个模块源码）②审计（脚本比对契约↔实现，零 Token）③防跑偏（契约外功能一律不做）。
- **收益**：模型不再需要"读整个工程来理解范围"，单模块上下文从几十万 Token 降到几千。

落地形态参考：`extract-contracts.ts`（正则/AST 提取）+ `contracts.json`（真值）。

## 2. 会话隔离：一个模块一个新会话

- 上下文账单的大头是**历史累积**：修复循环每轮都重发全部历史。模块完成后立刻收尾（提交+审计报告落盘），然后**开新窗口**做下一个模块。
- 跨会话续跑的三件套（缺一不可，否则新会话要重新探索，反而更贵）：
  1. **进度文档**（阶段状态表 + 已核实行为契约清单，新会话先读它）
  2. **契约真值 JSON**（范围与对齐基准）
  3. **Agent 持久记忆**（项目状态一句话摘要 + 真值文件路径）
- 经验数据：隔离后总消耗可降约 80%。

## 3. 分层执行：机械的归脚本，复杂的归模型

| 层 | 适用工作 | 执行者 |
|---|---|---|
| L1 纯机械 | 名称变换、DTO 字段映射、路由清单、文件拷贝/改名 | 脚本（零 Token） |
| L2 规则转译 | 分页/CRUD/树构建等模式化逻辑 | 快速模型 + 契约上下文 |
| L3 需要推理 | 复杂业务流、外部 API 签名、并发/事务语义 | 强模型，只喂该模块源码片段 |

- 让模型写"能生成代码的脚本"比让模型直接生成 90 个相似文件便宜一个数量级。
- 给模型的源码片段要定点：用 `grep -n` 定位后按行号区间读，**避免整文件大段读取**。

## 4. 自愈循环的代价控制

- "0 报错才交付"的红线正确，但要**给循环装上预算**：同类编译错误连续 3 次修不掉就停下来升级处理（换策略/换人），不要让模型无限重试。
- 验证尽量用**退出码**（tsc/build/审计脚本），不要用"让模型看日志找问题"——日志比对交给脚本，模型只处理脚本筛出的最小差异集。

## 5. 其他实务

- **Prompt Caching**：把稳定的大型规约（工程规范、契约 JSON、全局类型）放在提示词头部命中缓存，成本可降 50%+；每轮会话只把易变部分放尾部。
- **消耗遥测**：在任务粒度记录 Token 消耗（模块级最差/最佳样本对比），持续找出"最贵环节"做下一轮优化。
- **红线不省**：与正确性相关的验证（编译、契约审计、冒烟）一分钱不能省——省错地方返工才是最贵的。

## 6. 检查清单（开工前逐项确认）

- [ ] 已有机器可读契约/清单作为范围边界与验收基准？
- [ ] 已有脚本化审计（编译+契约比对）可零 Token 验证？
- [ ] 模块粒度是否切到"一个会话能干净收尾"？
- [ ] 跨会话续跑三件套（进度文档/真值/记忆）是否就位？
- [ ] 模型读取是否全部定点化（无整库大文件通读）？
